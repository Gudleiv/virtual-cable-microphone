# Виртуальный микрофон для ShadowPlay (Sound Blaster GC7) — ТЗ и промпт

## 1. Суть задачи

NVIDIA ShadowPlay пишет системный звук как WASAPI-loopback ровно с **одного** endpoint'а — дефолтного устройства вывода. Sound Blaster GC7 presentится в Windows как **два независимых устройства вывода**:

- `Speakers (Sound Blaster GC7)` — Default Device, сюда идёт игра
- `Headset (Sound Blaster GC7)` — Default Communications Device, сюда идёт Discord

Ручка GameVoice Mix микширует их **в железе, уже после Windows**. Поэтому голос друзей в записи отсутствует, и вернуть его из железа нельзя: у GC7 официально нет What-U-Hear.

Единственная точка входа, оставшаяся в ShadowPlay — выбор **микрофона**. Значит нужен виртуальный микрофон, содержащий `друзья + мой голос`.

## 2. Почему такая архитектура

Kernel-mode часть **не пишем**. Свой `.sys` потребовал бы EV-сертификата и attestation signing через Microsoft Partner Center; самоподписанный каталог не поможет (ядро использует свои trust anchors → Code 52), а TESTSIGNING ломает EasyAntiCheat и Vanguard.

Вместо этого kernel-часть берётся готовой и уже подписанной — **VB-CABLE A+B** (лицензия куплена). Пишем только **user-mode сервис**, которому подписи не нужны вообще и на который античиты не смотрят.

## 3. Схема сигнала

```
Игра ──────────────────► Speakers (GC7) ──► [ShadowPlay: системная дорожка]
                                       └──► уши

Discord ───────────────► Headset (GC7) ───► уши (GameVoice Mix работает, 0 мс)
                              │
                              │ WASAPI loopback (только чтение копии потока)
                              ▼
Микрофон (GC7) ──────►  [НАШ СЕРВИС: микс]  ──► CABLE-A Input
                              │                        │
                              │                        ▼
                              └── (Discord держит мик   CABLE-A Output
                                   параллельно,              │
                                   shared mode)              ▼
                                                    [ShadowPlay: дорожка «микрофон»]
```

Ключевое: loopback-capture чужого endpoint'а **не вклинивается** в тракт Discord и не добавляет ему ни миллисекунды. Discord и Windows не перенастраиваются вообще.

Итог записи в раздельных дорожках: дорожка 1 = чистая игра, дорожка 2 = друзья + свой голос.

## 4. Технические требования

### 4.1 Стек

- C++20, MSVC, CMake. Windows SDK. **Без сторонних зависимостей.**
- COM: `CoInitializeEx(nullptr, COINIT_MULTITHREADED)`.
- Консольное приложение на первом этапе, tray-иконка вторым.

### 4.2 Категорически не Windows Service

Аудио-endpoint'ы привязаны к сессии пользователя. Служба живёт в Session 0 и **не увидит устройств**. Автозапуск — задача планировщика «при входе в систему» либо ключ `Run`, процесс в пользовательской сессии.

### 4.3 Идентификация устройств

- Матчинг **по `IMMDevice::GetId()`**, не по friendly name: имена локализованы и меняются при перепрошивке/переподключении.
- Режим `--list-devices`: печатает `endpoint ID`, friendly name, дефолтные роли, mix format, число каналов. По нему пользователь заполняет конфиг.
- В конфиге допускается fallback-матчинг по подстроке имени, но с предупреждением в лог.

### 4.4 Три потока и кто главный по клоку

| Поток | Endpoint | Режим |
|---|---|---|
| Capture A | `Headset (GC7)` | shared + `AUDCLNT_STREAMFLAGS_LOOPBACK` |
| Capture B | `Microphone (GC7)` | shared, **никогда не exclusive** (Discord держит его параллельно) |
| Render | `CABLE-A Input` | shared, event-driven |

**Клок-мастер — render-клиент CABLE-A.** Он event-driven (`AUDCLNT_STREAMFLAGS_EVENTCALLBACK`), и на каждом событии тянет доступные кадры из обоих кольцевых буферов.

Причина: loopback-поток в shared mode ненадёжно работает с event callback — его надо **опрашивать**. Оба capture'а поллятся в своих потоках высокоточным waitable timer'ом и пишут в lock-free SPSC ring buffer; render-поток только читает. Никаких аллокаций и блокировок в аудио-пути.

### 4.5 Форматы

- `GetMixFormat()` на каждом endpoint'е, корректный разбор `WAVEFORMATEXTENSIBLE`.
- Внутреннее представление — float32 деинтерливед.
- **Требовать 48000 Hz на всех трёх.** При расхождении — внятная ошибка в лог с указанием, что поправить (`VBCABLE_ControlPanel.exe` → Internal Sample Rate; свойства устройства в Windows). Ресемплер — опциональная цель второго этапа.
- Каналы: loopback может оказаться **многоканальным**, если на GC7 включён режим SURR (7.1 virtual surround). Обязателен даунмикс >2ch → стерео. Микрофон моно → дублировать в стерео.

### 4.6 Компенсация дрейфа — обязательна

Три независимых клока (GC7 render, GC7 capture, VB-CABLE). Дрейф 100 ppm = **360 мс за час записи**. Для часовых прохождений это критично.

- Для каждого источника: целевой уровень заполнения кольца (~25 мс), измерение среднего заполнения на окне ~1 с.
- При отклонении — микрокоррекция скорости чтения (±0.1%) через дробную задержку/линейную интерполяцию. Резкие drop/insert допустимы только как аварийный откат при выходе за пределы кольца, с записью в лог.
- Уровни заполнения и накопленную коррекцию логировать раз в 30 с.

### 4.7 Микширование

- Независимые гейны для `chat` и `mic` в дБ из конфига, применяются без щелчков (сглаживание за ~10 мс).
- Лимитер на сумме (peak, без lookahead) — избежать цифрового клиппинга, когда друзья и ты говорите одновременно.
- Опционально: noise gate на микрофоне (порог, attack, release, hold). Отдельным флагом, по умолчанию выключен.

### 4.8 Живучесть

Это то, на чём разваливаются все самописные роутеры. USB-DAC переэнумерируется при сне/пробуждении и перетыкании кабеля.

- Реализовать `IMMNotificationClient`: `OnDeviceStateChanged`, `OnDeviceAdded`, `OnDeviceRemoved`, `OnDefaultDeviceChanged`.
- Ловить `AUDCLNT_E_DEVICE_INVALIDATED` на любом из трёх потоков → пересоздать **только этот** поток с экспоненциальным backoff (100 мс → 5 с, потолок).
- Пока источник мёртв — **не останавливать render**, кормить его тишиной. Разрыв в потоке ShadowPlay может выглядеть как отвал устройства.
- Тест: заснуть/проснуться, выдернуть и вставить GC7 — сервис должен восстановиться сам, без перезапуска.

### 4.9 Тишина в loopback

Когда Discord молчит, loopback может отдавать ноль пакетов, а не тишину. Обрабатывать:

- нулевое число пакетов → подмешивать тишину, не залипать;
- флаги `AUDCLNT_BUFFERFLAGS_SILENT` и `AUDCLNT_BUFFERFLAGS_DATA_DISCONTINUITY` обрабатывать явно;
- опционально держать открытым молчащий render-клиент на `Headset (GC7)`, чтобы клок endpoint'а не останавливался. За флагом в конфиге.

### 4.10 Приоритеты

- `AvSetMmThreadCharacteristics(L"Pro Audio")` на render- и capture-потоках, освобождать при выходе.
- Целевая добавленная задержка < 30 мс. Загрузка < 0.5% одного ядра.

### 4.11 Конфиг и логи

- `config.toml` (или INI — парсер свой, без зависимостей) рядом с exe: ID устройств, гейны, целевой буфер в мс, флаги, уровень логирования.
- Ротируемый лог-файл. При старте — сводка: выбранные устройства, их форматы, размеры буферов, расчётная задержка.
- Счётчики за сессию: xrun'ы, discontinuity, пересоздания потоков, накопленная коррекция дрейфа. Дамп в лог при выходе.

### 4.12 Tray (этап 2)

Иконка в трее: статус, mute mic, mute chat, reload config, exit. Индикация ошибки цветом иконки.

## 5. Не входит в задачу

- Kernel-mode драйвер, любые манипуляции с подписью, TESTSIGNING.
- GUI-микшер, эквалайзеры, эффекты.
- Изменение настроек Discord или дефолтных устройств Windows.
- Собственная запись видео/аудио в файл — пишет ShadowPlay.

## 6. План проверки

1. `--list-devices` — все три устройства видны, форматы 48 kHz.
2. Discord держит микрофон одновременно с сервисом, оба работают (shared mode не сломан).
3. Тестовый звонок: голос друга слышен в ушах как раньше, GameVoice Mix крутит баланс.
4. В ShadowPlay микрофон = `CABLE-A Output`, дорожки раздельные. Записать клип: дорожка 1 = игра, дорожка 2 = друг + свой голос.
5. **Замер рассинхрона:** хлопок в ладоши в кадре, измерить смещение аудиодорожки относительно видео. Смещение постоянное → фиксируется одним сдвигом в монтаже, но величину надо знать. Если > 60 мс — снижать Max Latency в `VBCABLE_ControlPanel.exe` и целевой буфер в конфиге.
6. Soak-тест 2 часа: рассинхрон не растёт, xrun'ов нет.
7. Sleep/wake и перетыкание USB — автовосстановление.

## 7. Известные внешние грабли

- **ShadowPlay сбрасывает выбор микрофона**, если во вкладке «Запись» Windows меньше 4 активных устройств. Включить показ отключённых и активировать до 4+.
- Системная дорожка ShadowPlay следует за устройством, назначенным процессу `NVIDIA Container` в «Параметрах громкости и устройств приложений». Если игра вдруг пропала из записи — смотреть туда.
- В `VBCABLE_ControlPanel.exe` зафиксировать 48000 Hz и минимальный стабильный Max Latency.

## 8. Промпт для Claude Code

> Пишем Windows-приложение на C++20 (MSVC + CMake, только Windows SDK, без сторонних зависимостей): резидентный user-mode сервис, который собирает виртуальный микрофон для записи в NVIDIA ShadowPlay.
>
> **Что делает:** WASAPI loopback-capture с одного render-endpoint'а (чат-выход Sound Blaster GC7, куда играет Discord) + обычный shared-mode capture с микрофона → микширует → рендерит в VB-CABLE A. ShadowPlay выбирает capture-сторону VB-CABLE A как микрофон и получает дорожку «друзья + мой голос», при этом Discord и настройки Windows не трогаются вообще.
>
> Полное ТЗ — в приложенном `gc7-virtual-mic-spec.md`, прочитай его целиком перед началом. Особое внимание разделам 4.4 (render — клок-мастер, loopback поллится, не event-driven), 4.6 (компенсация дрейфа обязательна — иначе за час записи набегают сотни миллисекунд), 4.8 (восстановление после переэнумерации USB) и 4.2 (это НЕ Windows Service — Session 0 не видит аудио-endpoint'ов).
>
> **План работы:**
> 1. Разложи задачу на этапы и покажи мне план, прежде чем писать код.
> 2. Этап 1: скелет проекта + `--list-devices` (перечисление endpoint'ов с ID, именами, mix format, ролями). Я запущу и пришлю вывод — по нему заполним конфиг.
> 3. Этап 2: три потока + lock-free SPSC ring buffers + микс, без компенсации дрейфа. Прогон, проверка звука.
> 4. Этап 3: компенсация дрейфа, лимитер, счётчики и логирование.
> 5. Этап 4: живучесть — `IMMNotificationClient`, обработка `AUDCLNT_E_DEVICE_INVALIDATED`, backoff.
> 6. Этап 5: tray-иконка и автозапуск через планировщик.
>
> После каждого этапа останавливайся, объясняй что сделано и что проверить. Не переходи к следующему без моего подтверждения. Комментарии и идентификаторы в коде — на английском. В аудио-пути никаких аллокаций, блокировок и логирования.
